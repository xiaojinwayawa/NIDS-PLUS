# NIDS 系统参数配置说明

本文档记录了 NIDS（网络入侵检测系统）底层核心参数的详细说明，特别是与流量聚合（Flow Aggregation）相关的延迟与内存控制参数。
在毕业设计答辩演示、或面对不同硬件配置（如 16GB 内存笔记本）时，可以通过调整这些参数来达到“秒级告警”和“防止内存溢出”的平衡。

---

## 1. 核心流聚合超时参数 (Flow Aggregation)

### 所在文件与位置
- **配置定义**：`backend/config.py`
- **配置接口**：`backend/api/routers/system.py`
- **实际生效位置**：`backend/ml/detection_engine.py`

### 参数详细说明

#### `FLOW_IDLE_TIMEOUT` (空闲超时)
- **有什么用**：判断一条网络流在多久没有新包后可立即结算。这个参数对“告警速度”影响最大。
- **默认值**：`5.0` (秒)
- **调小影响**：更快触发检测，适合短流攻击和答辩演示，但可能把持续流切得更碎。
- **调大影响**：流更完整，但告警会更晚出现。

#### `FLOW_AGGREGATION_TIMEOUT` (活动超时 / 强制超时)
- **有什么用**：持续有数据的长流即使不会空闲，也会在该时间到达后被强制结算，避免内存持续堆积。
- **默认值**：`120.0` (秒)
- **调小影响**：长流更早触发检测，但同一事件更可能被拆成多段。
- **调大影响**：更保留完整上下文，但长连接告警会更慢。

#### `FLOW_TCP_TIMEOUT` / `FLOW_UDP_TIMEOUT` / `FLOW_ICMP_TIMEOUT` (协议级超时)
- **有什么用**：分别控制 TCP、UDP、ICMP 流的协议级超时策略。
- **默认值**：
  - `FLOW_TCP_TIMEOUT = 120.0`
  - `FLOW_UDP_TIMEOUT = 120.0`
  - `FLOW_ICMP_TIMEOUT = 120.0`
- **调节建议**：
  - TCP 更关注连接持续性，适合中等或偏长超时；
  - UDP/ICMP 若你希望更快报警，可适当调小；
  - 若你希望三类协议行为保持一致，维持相同默认值即可。

#### `FLOW_MAX_PACKETS` (单流最大包数)
- **有什么用**：限制一条流最多缓存多少个包，用于保护内存。
- **默认值**：`500`
- **调大影响**：单流信息更完整，但内存占用上升。
- **调小影响**：更节省内存，但长流特征可能不完整。

#### `FLOW_ENABLE_BIDIRECTIONAL` (双向流聚合)
- **有什么用**：控制是否把双向通信视为同一条流进行聚合。
- **默认值**：`True`
- **调大影响**：保持双向特征完整，更适合真实会话分析。
- **调小影响**：可简化部分场景，但会损失回包相关特征，不建议默认关闭。

### 当前不建议配置化开放的底层参数
- `sequence_window_size`
- `sequence_step_size`
- `fin_immediate_close`

这些参数更偏底层机制，改动后更容易影响序列模型样本构造或流关闭逻辑，当前阶段建议继续保留在代码默认值中。

## 2. 检测节奏控制参数 (Runtime Timing)

### 所在文件与位置
- **配置定义**：`backend/config.py`
- **配置接口**：`backend/api/routers/system.py`
- **实际生效位置**：
  - `backend/ml/detection_engine.py`
  - `backend/ml/flow_aggregator.py`

### 参数详细说明

#### `PCAP_REPLAY_INTERVAL` (PCAP 回放间隔)
- **有什么用**：控制 `PcapReplayCapture` 在回放数据包时的发送节奏。
- **默认值**：`0.001` (秒)
- **调小影响**：回放更快，更接近压测；但更容易造成队列堆积和突发负载。
- **调大影响**：回放更平稳，更适合观察告警过程；但整体演示速度会变慢。

#### `FLOW_CHECK_INTERVAL` (流完成检查间隔)
- **有什么用**：控制检测主循环多久检查一次“已超时/可结算”的流，并把这些流送入推理。
- **默认值**：`0.5` (秒)
- **调小影响**：流更快进入检测，告警更及时，但轮询频率更高。
- **调大影响**：CPU 更省，但空闲超时后的流会更晚触发检测。

#### `PIPELINE_IDLE_SLEEP` (空轮询休眠间隔)
- **有什么用**：当 Redis 队列暂时没有新包时，主处理线程休眠多久再继续轮询。
- **默认值**：`0.05` (秒)
- **调小影响**：对新流量的响应更快，但空转轮询更多。
- **调大影响**：资源更省，但轻量流量场景下告警可能更迟钝。

#### `FLOW_CLEANUP_INTERVAL` (后台流清理间隔)
- **有什么用**：控制流聚合器后台清理线程多久扫描一次活动流，用于释放超时流并触发后续处理。
- **默认值**：`30.0` (秒)
- **调小影响**：流超时后的发现更及时，更利于低时延演示。
- **调大影响**：后台扫描开销更低，但超时流可能更晚被处理。

---

## 💡 总结：完美演示的最佳配置方案 (适用于 16G 内存)

如果你要进行毕业答辩，希望系统反应极快、不卡顿、内存不爆炸，请执行以下两步：

1. 通过系统配置接口调整：
   - `FLOW_IDLE_TIMEOUT = 2.0`
   - `FLOW_AGGREGATION_TIMEOUT = 60.0 ~ 120.0`
   - `FLOW_TCP_TIMEOUT = 60.0 ~ 120.0`
   - `FLOW_UDP_TIMEOUT = 5.0 ~ 30.0`（若你偏重短流快速结算）
   - `FLOW_ICMP_TIMEOUT = 2.0 ~ 10.0`
   - `FLOW_CHECK_INTERVAL = 0.2 ~ 0.5`
   - `PIPELINE_IDLE_SLEEP = 0.01 ~ 0.05`
   - `FLOW_CLEANUP_INTERVAL = 1.0 ~ 5.0`
2. 若需要更快的离线回放节奏，再额外调小 `PCAP_REPLAY_INTERVAL`

修改完成后，重启后端 API 服务即可生效。

## 3. 运行时误报抑制参数

### 所在文件与位置
- **配置定义**：`backend/config.py`
- **配置接口**：`backend/api/routers/system.py`
- **实际生效位置**：
  - `backend/ml/detection_engine.py`
  - `backend/ml/inference_engine.py`

### 参数详细说明

#### `FLOW_MIN_PACKETS` (极小流过滤阈值)
- **有什么用**：控制系统在流级推理前，至少要求一条流累计多少个包才送入模型。低于该值的流会被视为背景噪声或残缺流，直接过滤。
- **默认值**：`3`
- **调大影响**：误报会进一步下降，但可能漏掉极短的真实攻击探测流。
- **调小影响**：对短流攻击更敏感，但更容易把系统心跳包、广播包带进模型。

#### `MULTICLASS_CONFIDENCE_THRESHOLD` (多分类置信度缓冲阈值)
- **有什么用**：控制多分类模型在 `argmax` 之后，是否允许低置信度攻击标签直接触发告警。若预测为攻击但最大概率低于该阈值，则会被降级为 `Normal`。
- **默认值**：`0.80`
- **调大影响**：对误报更保守，只有高把握的攻击才会放行。
- **调小影响**：模型更激进，更容易快速报出攻击类型，但误报概率会上升。

### 使用建议
- **静默环境误报偏多**：优先提高 `MULTICLASS_CONFIDENCE_THRESHOLD`，例如从 `0.80` 调到 `0.85`。
- **本地背景心跳很多**：适当提高 `FLOW_MIN_PACKETS`，例如从 `3` 调到 `4` 或 `5`。
- **担心漏掉短流探测**：保留 `FLOW_MIN_PACKETS=3`，只微调 `MULTICLASS_CONFIDENCE_THRESHOLD`。

## 4. 告警事件化与去重参数

### 所在文件与位置
- **配置定义**：`backend/config.py`
- **配置接口**：`backend/api/routers/system.py`
- **实际生效位置**：
  - `backend/ml/alert_engine.py`
  - `backend/ml/detection_engine.py`

### 参数详细说明

#### `ALERT_EVENT_COOLDOWN_SECONDS` (告警冷却时间)
- **有什么用**：控制同一 `src_ip + attack_type` 事件在短时间内重复命中时，是否继续向前端重复广播。小于该时间间隔的重复命中只更新已有事件，不重新刷出新告警。
- **默认值**：`15`
- **调大影响**：告警更稳、更安静，重复刷屏更少，但用户看到事件更新的节奏会更慢。
- **调小影响**：界面刷新更频繁，更接近“实时连发”效果，但重复告警感会增强。

#### `ALERT_EVENT_RESOLVE_TIMEOUT_SECONDS` (事件结束超时)
- **有什么用**：控制同一告警事件多久没有再次命中后，被视为“已结束（resolved）”。
- **默认值**：`30`
- **调大影响**：系统更倾向于把间歇性攻击视为同一持续事件，事件结束会更晚。
- **调小影响**：系统会更快把攻击判定为结束，但若攻击是间歇式的，可能更容易被拆成多段事件。

### 使用建议
- **答辩演示想让界面更干净**：可把 `ALERT_EVENT_COOLDOWN_SECONDS` 调到 `20` 或 `30`。
- **想更快看到“攻击已结束”**：可把 `ALERT_EVENT_RESOLVE_TIMEOUT_SECONDS` 调到 `15` 或 `20`。
- **担心一次持续攻击被拆成很多段**：适当提高 `ALERT_EVENT_RESOLVE_TIMEOUT_SECONDS`。
- **推荐起步组合**：
  - `ALERT_EVENT_COOLDOWN_SECONDS = 15`
  - `ALERT_EVENT_RESOLVE_TIMEOUT_SECONDS = 30`

### 如何做到“可调节”
- 系统已将这两个值接入全局配置项，不再写死在源码里。
- 你后续可以通过系统配置接口统一调整，而不必再修改 `alert_engine.py`。
- 调整时建议在**系统停止状态**下修改，修改完成后重新启动检测服务以观察效果。
